# Phase 7 fixture-only workflow

Use `scripts/workflow.py INPUT.json OUTPUT.json` only for explicitly selected deterministic fixture replay. It validates a Phase 1 outcome contract and records caller-declared pass/fail steps through the Phase 3 journal. It does not invoke agents, build software, run acceptance verifiers or perform repository/external actions. Ordinary work keeps Deep Loop's existing execution, checkpoint, proof and delivery path.

The specification shape is [workflow.schema.json](../schemas/workflow.schema.json): absolute `contract`/`database` paths, nonblank `task`, recorded `authorization`, and nonempty `steps`, each exactly `key`, boolean `protected` and `result` (`pass` or `fail`). Results are declarations, not evidence. The wrapper validates full specification and contract before journal effects; blocked contracts and authority escalation beyond the recorded contract are refused. These recorded values never grant permission.

Initialization retains the exact contract SHA-256 in the journal's existing initialized event, using its optional `contract_sha256` plan field. Resuming requires matching contract bytes, ordered step keys/protection flags and recorded authorization. Result declarations may change for a diagnosed retry without changing acceptance authority. Legacy/unbound/mismatched journals are refused, not migrated/reset. Existing journal tasks without the optional field continue through the journal's own API.

Claims return an attempt number; the wrapper passes it back for completion/failure. A failure returns retryable/blocked according to the existing journal budget, with no automatic retry loop. An observed running step returns wrapper blocked while leaving the journal running: its owner may still be active. Inspect actual ownership/status first; only an explicitly authorized caller may invoke the journal recover action after confirming inactivity and reconciling uncertain effects. A refused claim can report wrapper blocked while `journal_state` remains ready; it does not claim to have changed that state. Completed fixtures retain their completed status on resume without replaying them. No fixture state marks a Deep Loop checkpoint COMPLETE or proves acceptance/SHIP.

The CLI reserves new output exclusively before journal changes, so an existing/concurrent output cannot advance the fixture. Rejected execution or interruption may leave an empty/partial reserved report; preserve it and diagnose before choosing a new path. Exit 0 means fixture journal completed, exit 1 means a noncompleted fixture report, exit 2 reports input, helper, timeout or I/O rejection. The API has no OS isolation or external exactly-once guarantee; concurrent wrappers still rely on journal claims and attempt checks.

Run `py -3 -B scripts/test_workflow.py`; the package suite includes it. Store no secrets in fixture results or journal references.
