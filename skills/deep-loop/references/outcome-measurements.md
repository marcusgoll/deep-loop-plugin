# Outcomes and delayed proof

Use this reference for an optimization comparison, a selected substantial task whose outcome will inform improvement, or delivery whose risk requires observation after immediate readback. Reuse the existing plan, acceptance contract, receipts and result artifacts; this adds no scheduler, tracker or monitoring service.

## Controlled comparisons

Before running, record the decision being tested, immutable baseline and candidate identities, declared cases and inputs, acceptance/endpoint, relevant environment, sample plan, and permitted operations. Keep these conditions comparable; disclose changes that prevent a like-for-like conclusion. Preserve the baseline and failed runs. Separate setup mistakes from an observed task failure without deleting either.

Start with a small reversible edit, an interrupted multi-slice task whose evidence changes, and a failed verifier or unavailable delivery endpoint. Exercise changed UI, iOS or coordinated adapters with their applicable proof; unchanged adapters retain their existing scoped evidence. A local fixture proves that fixture's behavior, not a live/native endpoint. Use actual saved-artifact inspection for the tiny edit; it need not acquire a checkpoint solely for the benchmark.

For each run, retain the input/source identities, actual invocation or attributable action, native result, saved artifact/readback, observed incomplete or complete disposition, and the measurements below. Re-run required proof after material changes. Count unsupported completion only by comparing the claimed endpoint with its required actual evidence; a correctly blocked case is a correct outcome, not a successful delivery.

Use all declared repetitions and report the distribution or preselected statistic. Do not select the fastest run. If order, warm-up, machine load, retries or changed scope could influence the comparison, retain those conditions and narrow the conclusion. Identical helper code with different guidance can demonstrate CLI compatibility; its timings do not measure the guidance's effect on an agent's delivery.

Compare correctness first: no unsupported completion, preserved attributable decisions, correct recovery and missing-proof handling. Report process overhead separately. After baseline measurement, propose improvement thresholds with the measured range, tradeoff and uncertainty for owner approval. Until approved and demonstrated, keep the efficiency research gate pending; do not invent a target or claim the optimization as a whole is proven.

## Measurements from existing records

For selected substantial real tasks, derive a compact local summary from the records already retained. Each reported value identifies its source, unit, boundaries, inclusion rule and missing data. Missing observations are **unknown**, not zero. Do not add mandatory telemetry to tiny work, copy secrets into a report, or send external telemetry.

| Measure | Derivation and boundary |
| --- | --- |
| Lead time | Difference between attributable start and endpoint timestamps. Name those events, clock source and pauses included. An intent-to-result-record interval is recorded elapsed time, not active work, CPU time or endpoint latency. Reject reversed or incomparable timestamps. |
| Rework | Observed corrections or repeated work attributed to a defect, with receipt links. Distinguish planned RED controls, setup corrections and material repair; tests run or iterations are not themselves rework counts. A scoped observed correction count is not an exhaustive rate. |
| User interventions | Actual attributable requests needed to resolve or redirect execution, distinguished from initial authorization and planned design decisions. Use unknown if the available records cannot establish coverage. |
| Recovery | Expected invariant and observed result when resuming after interruption/change. Count only inspected recovery attempts and errors; no observed error in one fixture does not prove all recoveries work. |
| Resources/overhead | Observed operation count, command elapsed time, output bytes, token/CPU/memory/cost data only where the facility exposes them. Define the observation interval and what is excluded. Wall time does not establish CPU use or cost. Requested model configuration does not establish execution identity. |

A useful comparison row contains case ID, revision, result, elapsed boundary/value, attributable rework/interventions/recovery, observed resource values or unknown, and evidence links. Keep the raw receipts so another reader can recompute it. Do not collapse missing metrics into a fabricated score or infer savings from a role/model label. Selected task observations complement controlled cases; different inputs or endpoints cannot establish a causal baseline/candidate improvement.

## Delayed proof

When background jobs, synchronization, migrations, sustained load or another material risk is not proved by immediate readback, define observation acceptance **before delivery** in the existing contract/plan:

- target and delivered revision, failure invariant and probes;
- observation conditions: relevant events/load/cycles or justified duration, sample coverage, expected outcomes and freshness;
- authorized execution facility and owner, artifact/readback requirements, and failure/recovery action.

Choose conditions from operational requirements or measured behavior. A duration alone is insufficient without the required probes and coverage; there is no universal waiting period. A probe performed before the relevant event cannot prove the post-event outcome. Immediate readback can remain sufficient for a saved artifact or other endpoint whose agreed invariant it actually proves.

Reuse existing required checks at `stage: ship` and [Verification Contract integration](verification-contract-integration.md). Deterministic observation uses an approved verifier that evaluates the declared conditions, preserves all required samples and fails for missing, stale or failed proof. Its existing bound invocation, inputs and artifacts establish captured identity; the agent independently inspects the native report and actual target. Do not add arbitrary observation fields to the checkpoint schema or treat a generic evidence string as enforced timing/coverage. Truly manual judgments remain explicitly manual; deterministic proof must not be relabeled to bypass a blocker.

While required observation is pending, failed, stale or unavailable, delivery stays incomplete even if deployment or immediate readback succeeded. Keep the relevant check pending/failed and preserve evidence and the smallest next action. The helper can validate declared receipts and recorded gates; it does not continuously watch the target, authenticate a person, infer elapsed observation coverage, or create probe results.

## Unavailable proof and recovery

Inspect the actual capability or setup failure and investigate within existing authority. A bounded repair or alternative is suitable only if it proves the **same invariant** for the required target/revision and observation conditions. Retain why it is equivalent and its actual results. Local downloaded reports, dry runs or narrower samples do not waive required live/device/load proof.

Continue independent authorized work while the affected requirement remains incomplete. If the remaining option needs a missing capability or new authority, report the failed probe/setup, affected acceptance, retained result, and smallest external step. Recheck the blocker when resuming rather than assuming it persists or cleared.

Future or background observation requires an authorized existing runtime/monitor with inspectable execution and results. A saved prompt, planned schedule, queued job or promise to check later is not observation. Where no facility is authorized/available, report pending external observation; do not imply this chat is monitoring. If one is authorized, use its supported tool and inspect actual probe results before completing the agreed outcome. This reference creates no automation and grants no deployment or messaging authority.
