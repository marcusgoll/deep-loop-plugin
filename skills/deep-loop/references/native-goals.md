## Native goals

Assess goal suitability once the objective and endpoint are clear. Recommend a native goal for substantial implementation, work likely to span sessions, or coordinated delivery where runtime continuation would help. Skip the recommendation for small fixes, explanations, and planning-only work. Check `get_goal` first when available: reuse a matching unfinished goal under its current runtime status rather than offering a duplicate; an unrelated goal needs the user's direction.

When a goal would help and none matches, ask one concise question through the host's supported question tool: "Use a Codex goal to carry <settled objective> through <agreed endpoint>?" Use chat if no suitable tool is available. A clear affirmative answer requests that specific goal. While the answer is pending, continue independently authorized task work without creating a goal. Silence is not consent, and a declined goal does not block ordinary delivery. Retain the pending/accepted/declined choice in the existing plan or task context so compaction does not trigger repeated offers; revisit only when a material scope change warrants it. If goal tools are unavailable, continue with checkpoints instead of offering an unavailable capability.

When the user explicitly requests a goal, use the runtime's `create_goal` tool with the settled objective and delivery endpoint. The request authorizes goal creation; it does not select an otherwise unresolved endpoint. Recover endpoint authority from the user, repository, or an accepted contract. If none settles whether success means a local artifact, pull request, merge, release, or deployment, ask before creating the goal; do not make the objective concrete by adding a self-authored exclusion such as "do not push or deploy." A request to use Deep Loop alone is not a request to create a goal. Set `token_budget` only when the user explicitly requests one; budgets and continuation mechanics belong to the runtime.

Call `get_goal` before creating or resuming goal work. Reuse an unfinished goal only when its objective matches the authorized task; an unrelated unfinished goal requires the user's direction. Do not overwrite it or create competing goals for implementation slices. If goal tools are unavailable, report that limitation and continue the authorized checkpoint workflow without claiming a native goal exists.

The native goal owns runtime status; `state.json` owns acceptance and delivery evidence. When checkpointing, record the native objective in optional `state.json.goal.objective` and recheck it with `get_goal` on resume. A checkpoint never grants goal authority or proves runtime status.

Use only goal operations exposed by the current runtime. The available `update_goal` statuses do not provide native objective/budget editing or an active/resume setter. Changing the plan does not change the native objective. Resolve material objective changes with the user and report any runtime limitation; never mark unfinished work complete merely to replace its goal.

For an explicit user resume of a blocked goal, call `get_goal` once, recover the matching checkpoint and recheck the blocker. If the runtime has already reactivated the goal, continue normally. If it still reports `blocked` and exposes no resume setter, do not retry unsupported status mutations or create a replacement goal: treat the user's message as authority to resume the task, keep the native status explicitly recorded as platform-owned stale state, and continue the active checkpoint. Recheck native state before final completion and report the limitation without claiming the goal was active. This is the strongest local recovery path; only the runtime can make the native status transition.

After SHIP validation and independent readback, use `update_goal` with `status: complete` only when the goal's entire objective is achieved and no required work remains. For budgeted goals, report final token usage returned by the tool. Pause only at the user's explicit request, report the returned status, and stop goal work. Mark blocked only after the same condition repeats for at least three consecutive goal turns with no meaningful progress possible without user input or external change; resuming a blocked goal starts a fresh audit. Runtime tool instructions govern all status changes. An incomplete checkpoint, a delivery failure, or a nearly exhausted budget alone never justifies marking a goal complete.
